# 2026-11-05 実走障害の調査

これは当時の調査記録です。監視方式はその後、[単発フック方式](../muse/HOOKS.md)に変更されました。以下の常駐方式の調査・未実施事項は当時の状態を示し、現在の検証状況は[iOS README](../livetrack-receiver-ios/README.md)を参照してください。

## 1. モニターの連続ポーリング失敗

原因未特定。報告のabort/poll failingはJSONのok:false経路で発生する。
例外・60秒タイムアウト・JSON解析失敗はloop_errorで、連続失敗カウンタを増やさない。
ポーラーは.monitor.lockを取得しない。load_pendingは起動時に終了処理の別状態を読む。
従って親のロックによる直接のデッドロックはコード上確認できない。
ただし状態ファイルは0600、ディレクトリは0700へ変更するため、別ユーザー実行では
権限差が起き得る。手動と常駐プロセスのUID・実行環境・配備版の一致は未確認。
同じ状態への並行書き込みは原子的でも更新競合を防ぐものではない。

追加ログ: poll_failureに終了コード・所要時間・stderr要約・応答内容、
poll_exceptionに例外種別・途中出力を記録。既知トークン・セッションID、URL、
資格情報フィールドをマスクし長さを制限。判定やタイムアウト値は変更しない。

### 実セッション連続試験（未実施）

この開発環境には実走中のセッションと本番VMへの実行経路が提供されていない。
スタブ結果を実セッションでの検証と置き換えない。

1. 室内で時計のアクティビティとLiveTrackを開始し、更新版をVMへ配備する。
2. 通常のウォッチャー経由でモニターを起動。設定のpoll_interval_secを実装と照合し20秒にする。
3. 20分以上継続し、coach_logのpoll成功・poll_failure・poll_exception・loop_errorを集計する。
   publisher処理時間もあるため、取得時刻間隔も記録し「厳密な20秒周期」と混同しない。
4. 失敗時は新規ログのHTTP状態・error種別・所要時間・終了コードを確認。
   手動試験は同じユーザー・python3の解決先・cwd・設定・配備ファイルのハッシュを比較する。
   環境変数の値やargvのトークンをログへ出さない。
5. 状態共有の影響を切り分ける対照試験は、監視を停止して同じ状態で順次実行するか、
   安全な別ディレクトリの状態コピーで行う。同じ状態へ並行実行して結果を混ぜない。
6. 20分以上の成功数、失敗数、開始終了時刻、実行版を記録して共有する。

## 2. TTS完了扱いでも無音

原因未特定。現行コードではアプリ音声セッションを有効化して発話している。
発話音量を1.0と明示し、要求・didStart・didFinish時にルート種別、端末出力音量、
発話音量、voice識別子、セッション管理フラグを記録する。機器名・本文は追加ログに出さない。
完了コールバックは音が耳に届いたことを証明しないため、テキストのみのメッセージ配信をSpotify再生中に
同じイヤホンで行い、スピーカーでも比較し、聴取結果と診断ログを合わせて確認する。現在の設定画面の音声テストは同梱MP3であり、TTSの試験ではない。
この環境では実機の音を聴取できず、聞こえることは未確認。自動的な再発話は追加しない。

## 3. MP3準備失敗

原因未特定。URLSession.data(for:)の完了後にプレイヤーを生成しているため、
取得途中のDataを渡す経路は見つからない。ただしサーバーが返す音声自体の不正・
切断・ルート状態は当時の記録から判断できない。
セッション有効化がprepareToPlayの後だった順序を有効化→生成→準備に変更。
取得バイト数と準備失敗時のルート・音量を追加記録する。再試行回数は変えない。
実機で初回開始音声を複数回（Spotify再生中・停止中、イヤホン・スピーカー）確認し、
準備失敗件数と聴取を記録する。過去事象の再現・初回成功の実機確認は未実施。
