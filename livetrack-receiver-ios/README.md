# Voice Coach for Muse — iOSネイティブ版

Swift / SwiftUI、iOS 17以降、外部依存なしの受信用アプリです。標準Bundle IDは `jp.discoverroutes.livetrackreceiver`。Worker（データの受け渡し）からqueue.jsonとMP3を読み取ります。再生完了ACKや削除は送りませんが、開始検知と発話間隔の同期のためGAS（開始メール検知）を呼び出します。

**現況（2026-11-10）:** 実機で、Spotify再生中のダッキングと音声終了後の音量復帰、ロック中・バックグラウンドでの新着受信と再生、開始検知（アプリ→時計の順序）から終了処理までの実走フローを確認済みです。2026-11-08には話題系メッセージのiOS TTS読み上げを実走で確認し、2026-11-10には全メッセージのMP3配信（合成失敗なし）と、毎朝の話題バッチを取り込んだ発話を確認しました。残る未検証項目は [UI-UX.md](UI-UX.md) の「再検証項目」にまとめています。下記の検証記録は2026-11-01時点のものです。

## 最短の実機セットアップ

1. MacでXcodeを起動し、`Xcode > Settings > Accounts`（版によってApple Accounts）からApple IDを追加します。アカウント認証や利用規約の同意は本人が行ってください。
2. `Voice Coach for Muse.xcodeproj` を開きます。Package追加、npm、CocoaPodsは不要です。
3. 左のプロジェクトから `TARGETS > Voice Coach for Muse > Signing & Capabilities` を開きます。
4. `Automatically manage signing` をONにして、Teamに自分の **Personal Team** を指定します。Team IDや証明書は納品物に含めていません。
5. Bundle Identifierが取得できない場合は、自分用の一意な値（例：`jp.discoverroutes.livetrackreceiver.yourname`）へ変更します。
6. iPhoneをUSBで接続し、ロック解除します。「このコンピュータを信頼」が出たら本人が確認します。
7. Xcodeの実行先で実機を選びます。必要なOSサポートのダウンロードがある場合は完了させます。
8. iPhoneの `設定 > プライバシーとセキュリティ > デベロッパモード` をONにし、案内に沿って再起動・確認します。項目がない場合は先にXcodeとのペアリングを完了してください。
9. スキーム `Voice Coach for Muse` を選び、Run（⌘R）でビルド・インストールします。
10. 「信頼されていないデベロッパ」等が表示された場合のみ、iPhoneの `設定 > 一般 > VPNとデバイス管理` から自分の開発用Apple IDを信頼します。OSの案内に従ってください。
11. iPhoneにBluetoothイヤホンを接続してSpotifyを再生し、このアプリへ戻り、設定画面の **音声テスト** を押します。初回のダッキング確認は「コーチング開始」も位置情報の許可も不要です。

無料Personal Teamのプロビジョニングプロファイルは発行から7日で失効します。失効したら同じMac・Apple Accountで再ビルドし、上書きインストールしてください。アプリを削除するとUserDefaultsの設定・再生済み記録も消えます。有料のApple Developer Programでは7日間の制限はなくなりますが、プロファイルの期限や署名設定は確認してください。詳しくは[SETUPのステップ3](../SETUP.md#step-3)を参照してください。

### Capabilities制限に当たった場合

`Voice Coach for Muse-Foreground` スキームを選んでRunしてください。これは `DebugForeground` / `ReleaseForeground` 構成を使い、`UIBackgroundModes`と位置情報利用目的キーを含まない別のInfo.plistでビルドし、位置情報更新も無効化します。前景の受信・ダッキング・履歴機能は維持します。

署名画面でBackground Modes自体が拒否される場合は、前景構成を選んだうえでCapabilities欄のBackground Modesを削除し、再ビルドしてください。位置情報用途を説明するための無音ループなどは実装していません。

Personal Teamでの署名済み実機ビルド・インストールは実施済みで、Background Modes由来の制限は確認されていません。エラーが出た場合はXcodeの全文を検証記録へ残してください。

## 発話間隔（1.4.5 / 16）

設定の「発話間隔」で **1km / 500m / 3分 / 1分** を選びます。初期値は3分で、UserDefaultsに保存します。受信中も変更でき、約30秒ごとのGASスクリプトの呼び出しに `speech_interval` を含めます。検知後・監視開始後も同期し、停止・closedで終了します。30分の検知期限と15分の案内は、開始メール待ちの間だけ適用します。

GAS・Worker・Museのwatcher/monitorも更新が必要です。更新方法と反映確認は [SETUPのステップ5](../SETUP.md#step-5) を参照してください。ラン中の間隔変更は、2026-11-08の実セッションで1分→3分への切替を確認済みです（前回の送信を基準に反映されます）。3分→1分への切替は未検証です。

## 操作

画面構成の詳細は [UI-UX.md](UI-UX.md) を参照してください。

- **開始／停止**：メイン画面の電源ボタンでトグルします。開始すると設定URLを即時取得し、その取得完了から設定間隔（初期5秒）ごとに取得します。検知設定がある場合は、あわせてGASスクリプトを実行して開始メールの確認を依頼します。停止するとポーリング・取得・再生・待機を停止し、Audio Sessionと位置情報更新、自動ロック抑止を解放します。再生途中のIDは再生済みにしません。
- **音声テスト**：設定画面から実行します。同梱の `test-coaching.mp3` をMP3再生経路で再生し、音楽の音量低下と復帰を確認します。ネット接続不要です。通信エラーで再生が停止している場合は、受信を停止してから試します。実行不可の理由は設定画面に表示します。配信された MP3 とテキストのみの読み上げは、[SETUP のステップ7](../SETUP.md#step-7)で別途確認します。キュー再生とは重なりません。
- **再生済みをリセット**：履歴画面から実行します。全配信元・全セッションの成功IDを削除します（確認ダイアログ付き）。受信中なら次のポーリングで再検出します。
- **詳細ログ**：設定→「詳細ログ」で表示し、最大2,000行をクリップボードへコピーできます。ログ時刻はUTC、画面の履歴時刻は端末の現地時刻です。
- **設定**：URL類、間隔、自動ロック抑止、位置情報更新をUserDefaultsへ自動保存します。読み取りキーと検知スクリプトキーはKeychainに保存し、既存の検知キーは保存に成功した場合に移行します。接続先URL・検知設定と新着の確認間隔は開始中／再生中に変更できません。発話間隔は受信中も変更できます。
- **音声を再開**：OSが自動再開を許可しなかった場合やイヤホン切断後に表示します。

「Worker エンドポイント」に自分のWorkerのURLを直接設定します。既存の保存済みURLは維持され、切替・サンプルボタンはありません。「新着の確認間隔」はWorkerへ確認する周期（既定5秒）で、発話間隔とは別です。

## Museとのデータ契約

```json
{
  "session": "2026-11-01-longrun",
  "messages": [
    {
      "id": "m-0001",
      "ts": "2026-11-01T10:15:30+09:00",
      "audio": "audio/m-0001.mp3",
      "text": "5キロです。平均ペースは5分40秒。予定通りです。"
    }
  ]
}
```

- Museが更新できるHTTP(S)配信先を別途用意し、音声を先に配置してからJSONを追記／置き換えてください。
- audioの相対パスはqueue.jsonのURL基準です。tsはタイムゾーン付きISO 8601（小数秒も対応）。各取得内でts順にソートします。
- 同じ配信元URL・session・idを成功再生した場合は二重再生しません。sessionが変われば同じidも新規扱いです。URLのクエリを変えた場合も別の配信元になります。
- インストール後などの初回同期では、既存のメッセージを自動再生せず再生済みとして記録します。その後も、未検出の古いメッセージは自動再生しません。
- 音声が失敗しても文面は表示し、履歴に再生エラーと記録します。同じ開始期間中は失敗IDを繰り返さず、停止→開始またはアプリ再起動で再試行できます。
- 不正なJSON全体は当該取得を失敗として次回へ継続。idが空／tsが不正の要素はログに残し除外します。
- HTTPSを推奨。HTTP入力は受け付けますが、ATSにより拒否される配信先があります。全通信を許可するATS例外は入れていません。
- ネイティブのURLSessionにはWebブラウザのCORS制限はありません。Workerの読み取りには `X-Read-Token` を使います。読み取りキーはKeychainに保存し、Workerと同じHTTPS接続先にのみ送ります。

## 音声セッションの実装

1. テキストを表示してMP3を取得します。ネットワーク待ちだけでSpotifyを小さくしないよう、有効化は音声の取得・デコード準備の後です。
2. `setCategory(.playback, mode: .spokenAudio, options: [.duckOthers])` を設定し、`setActive(true)` を呼びます。
3. AVAudioPlayerで1件ずつ再生します。キューが続く間は約0.3秒間隔。Audio Sessionは同じバッチの間保持し、次のMP3取得待ちにも有効である場合があります。
4. 全件終了、停止、再生エラー時に `setActive(false, options: [.notifyOthersOnDeactivation])` で解放します。

セッション有効化／解放のAPI成功はログに記録しますが、Spotifyの実際の音量変化は検出できません。出力ポートや音量は強制変更せず、現在のBluetooth等の経路に従います。

電話等の割り込み開始時はキューを一時停止し、OSがセッションを無効化した状態を反映します。終了通知の `.shouldResume` があれば再有効化して続きから再生します。OSが再開を許可しない場合は、強制再生せず「音声を再開」で続行できます。経過秒数には割り込み待機時間を含みます。

イヤホン切断時も一時停止して手動再開を要求します。音声サービスのリセットでは受信を停止して再開始を案内します。途中停止した音声は成功IDとして保存しません。

## バックグラウンドの範囲と限界

通常スキームでは `UIBackgroundModes = [audio, location]` を指定します。開始中かつ位置情報更新トグルONのときだけ、CoreLocationの標準位置更新と `allowsBackgroundLocationUpdates` を有効化します。位置更新の内容は即座に破棄し、保存・ログ出力・サーバー送信はしません。位置情報の許可ダイアログにはこの用途を日本語で明示します。

初回は「アプリの使用中」の許可を要求します。「常に許可」は設定画面の専用ボタンで段階的に要求できます。OSによっては後から設定アプリで変更する必要があります。開始済みの標準位置更新は使用中許可でもバックグラウンド利用できる場合がありますが、許可や表示状態によって挙動が変わります。

- Audioモードだけでは、音声を再生していない長い待機時間のポーリングを保証できません。
- 位置更新が有効でも、5秒ちょうどのポーリングは保証できません。省電力・通信・権限・OSのプロセス制御に依存します。
- 位置情報拒否、前景専用構成、強制終了などではロック中の新着受信を保証しません。強制終了後に自動起動する仕組みはありません。
- `isIdleTimerDisabled` は開始中のみ設定します。手動ロックを阻止するものではありません。
- App Store配布では、受信継続のために位置更新を使い、その値を破棄する現在の実装が、[Appleの審査ガイドライン](https://developer.apple.com/app-store/review/guidelines/)のバックグラウンド利用・位置情報利用の要件（2.5.4、5.1.5）に適合するかが課題です。配布には設計の見直しが必要で、審査通過は保証できません。

## アプリ開始を基準にするLiveTrack検知

通常操作は「アプリでコーチング開始 → ウォッチでアクティビティ開始」。
開始時のUUIDとUTC時刻を保存し、GASへのPOST本文で `key` / `start_id` / `since` を渡す。
待機中のアプリ再起動では同じ要求を再開し、停止→開始では新しく生成する。
15分通知済みフラグも保存し、30分の上限は元の開始時刻から数える。
GASのfoundは検知だけを意味する。監視中表示は認証付きstart-status.jsonの
自分の開始IDがmonitoringになったときだけで、当日queue名では判定しない。

配置はWorker・VMを準備後、新アプリを先に配布し、GASの既存デプロイを
「新しいバージョン」で更新する（/exec URL維持、新規デプロイ不要）。
GAS更新後はGETを使う旧アプリでは検知できず、新アプリもPOST未対応の旧GASでは検知できない。
詳細は [GAS手順](../gas/README.md) を参照。

## 1.4.6 (17) の音声テストと待機処理

音声テストは同梱MP3へ変更しました。TTSの実聴取確認はSETUPのテキストのみ配信で行います。TTS・MP3の開始前に一時停止／割り込み／案内発話の終了を待つ処理は30秒で失敗として返し、待機開始・理由・終了またはタイムアウトを記録します。TTSが聞こえない実機問題の原因解決を示す変更ではありません。

音声テストでは再生開始時の出力先と端末音量を表示し、詳細ログに保存します。「再生処理が完了」はOSからの完了通知を示し、実際に聞こえたことを保証しません。聞こえない場合は、テスト再生中に音量ボタンとコントロールセンターの出力先を確認してください。
