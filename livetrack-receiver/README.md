# Muse LiveTrack コーチング受信ページ

静的HTML / CSS / JavaScriptのみ。ビルド・npm・バックエンド不要です。Museが配置するJSONとMP3を読み、単一のaudio要素で順次再生します。GarminへのアクセスやサーバーへのACKは行いません。

## 配置方法

1. `livetrack-receiver/` をフォルダごとXServer等の公開ディレクトリへアップロードします。
2. `https://あなたのドメイン/livetrack-receiver/` をiPhone Safariで開きます。
3. イヤホンをiPhoneに接続し、「コーチング開始」をタップします。0.15秒の確認音が鳴り、受信が始まります。

HTTPS推奨（Wake Lock・クリップボードに必要）。ファイルを直接開く `file://` ではfetchできません。サーバーは `.json` を `application/json`、`.mp3` を `audio/mpeg` で配信してください。

Mac等でのローカル確認（Pythonがある場合）：

```sh
cd livetrack-receiver
python3 -m http.server 8000
```

Chromeで `http://localhost:8000/?demo=1` を開きます。iPhoneのlocalhostはiPhone自身を指すので、iPhoneテストにはHTTPSホスティングを利用してください。

## Museからの配信

同梱の `queue.json` は空の本番用ひな形です。ページと同じディレクトリに置き、音声を先にアップロードしてからJSONに追記します。JSONは一時ファイルに書いて置き換えるなど、途中のJSONを配信しない更新方法を推奨します。

```json
{
  "session": "2026-11-01-longrun",
  "messages": [
    {
      "id": "m-0001",
      "ts": "2026-11-01T10:15:30+09:00",
      "audio": "audio/m-0001.mp3",
      "text": "5キロです。平均ペースは5分40秒。予定通りです。"
    }
  ]
}
```

- sessionは走行ごとに変更し、同一session内のidは一意で不変にします。messagesは時系列順に追記してください。受信側も各取得結果をts順に並べます。
- tsはタイムゾーンを含むISO 8601。audioは**queue.jsonのURL基準**の相対パス、またはHTTP(S)のURLです。音声はMP3で用意してください。
- 再生済み記録は「設定した配信元URL＋session＋id」単位です。デモと本番は分離されます。配信元URLを変えると別の記録になります。
- 初回はJSONに含まれる未再生メッセージすべてを再生します。古いメッセージを配信したくない場合はMuse側で除外してください。
- 別ドメインのqueue.jsonは配信側でCORS許可が必要です。HTTPSページからHTTPの配信先は使用しないでください。
- 位置情報やLiveTrackトークンを入れないでください。認証機能はありません。公開URLに置いたコーチング文やMP3はURLを知る人が閲覧できます。

## 設定と操作

| 項目 | 動作 |
| --- | --- |
| queue.jsonのURL | 初期値 `queue.json`。ページを基準に解決します |
| ポーリング間隔 | 初期値5秒。1〜300秒の整数。各取得完了後に次の取得まで待つ時間です |
| テスト再生 | 同梱の2秒のトーンを再生。待機・再生中は割り込まず操作メッセージを表示 |
| 再生済みをリセット | 受信後は直近の配信元・sessionを消去。受信前はこのアプリの全再生済み記録を消去。再生中は操作を保留 |
| ログをコピー | 最大2,000行をコピー。利用不可の場合は選択可能なテキスト欄を表示 |
| 音声を再開 | 自動再生が拒否された場合に表示。タップで待機音声を再試行 |

設定と**正常終了した音声のid**をlocalStorageへ保存します。再読み込み後も開始タップは必要ですが、再生済みは繰り返しません。再生途中で閉じた音声は次回再生対象です。履歴は現在のJSONから復元し、ログはページを開いている間だけ保持します。ストレージが使えない場合は画面とログで通知し、そのページ内のみ重複を防ぎます。

JSON取得はタイムスタンプクエリ＋no-storeでキャッシュを回避し、10秒で打ち切ります。失敗しても次回ポーリングを続けます。音声は読み込み、またはバッファ待ちが5秒続くとスキップします。エラーが即座に判明した場合は直ちにスキップします。スキップしたidはそのページ内では再試行しませんが、再生済みには保存しないため、リセットまたは再読み込みで再試行できます。正常な5秒以上の音声は途中で切りません。音声の間隔は約0.3秒です。

## デモ

`https://あなたのドメイン/livetrack-receiver/?demo=1`

「コーチング開始」後、確認音→440Hz・554Hz・659Hzのトーン（各2秒）を順次再生します。文面は画面用で、MP3は読み上げではありません。`demo-queue.json` と `demo-audio/` を使用し、設定した本番URLは読みません。再読み込み後はデモも重複再生しないため、もう一度試す場合は「再生済みをリセット」を押します。

トーン音声はこの納品用に合成したものです。製作用ツールは配備・利用に不要です。

## iOSでの注意点

開始ボタンのイベント内で、同じaudio要素のplay()を直接呼び、以後もその要素を使い回します。それでもSafariの状態によって拒否される可能性があるため、再開ボタンを用意しています。開始確認音自体もSpotifyへの割り込みになるので、ログの「開始確認音」とコーチングのidを区別して確認してください。

Wake Lockは対応環境で開始後に取得し、ページが表示状態に戻ると再取得を試みます。失敗しても音声・受信は継続します。画面の手動ロック、低電力モード、バックグラウンドでの受信・連続再生を保証するものではありません。静的ページのポーリングはiOSにより停止されることがあります。基本運用はSafariを前面に表示したままです。

Spotifyの停止・ダッキング・自動復帰は本ページから制御も検出もできません。Spotifyの音量は変更しません。v1.1ではAudio Session API対応時にambientを指定し、同時再生を要求します。受信設定でtransient、transient-solo、autoも比較できます。指定の成功はSpotifyとの共存を保証しません。ambientでは端末の消音設定にも注意してください。実機の耳で検証してください。

設計時の参考：[WebKitの自動再生ポリシー](https://webkit.org/blog/6784/)、[Wake Lock仕様](https://www.w3.org/TR/screen-wake-lock/)。

## 実走テストのチェックリスト

安全な場所で停止した状態で設定し、まず短い試走で確認します。

- [ ] iOSバージョン、iPhone機種、イヤホン、Safari、Spotify、低電力モードの状態を記録
- [ ] Spotifyを再生してから開始し、開始確認音がイヤホンに届く
- [ ] 3件が順番に鳴り、重ならず、履歴・id・開始終了時刻がログに残る
- [ ] コーチング時、Spotifyが一時停止／小音量化／変化なしのどれかを記録
- [ ] 各音声終了後、Spotifyが自動復帰するか、何秒で戻るかを記録
- [ ] 必要ならデモ完了後にSpotifyを再生し直し、Safariへ戻って「テスト再生」で単発割り込みを確認
- [ ] ページ再読み込み→開始で3件が再生されない（開始確認音は鳴る）
- [ ] queue.jsonに新しいidとMP3を追記し、次のポーリングで一度だけ再生される
- [ ] 存在しないMP3でもテキストが表示され、エラーの後に次の音声へ進む
- [ ] 一時的に通信を切って戻し、ポーリングが復帰する
- [ ] ロック画面／Spotify前面／Safari前面のそれぞれで受信と再生の挙動を記録
- [ ] Wake Lockが有効と表示され、Safari前面で通常の自動スリープ時間を超えても画面が点灯する
- [ ] 「ログをコピー」で時刻と耳で聞いた挙動を対応付ける（ログはUTC、履歴と最終成功時刻は端末の現地時刻）

実機でのSpotify・Bluetooth・ロック画面の確認は別途必要です。本納品の検証範囲は `VALIDATION.md` に記載しています。

## v1.1：Spotify停止への対策

初期値をambient（同時再生を要求）にしました。再読み込み後に画面下部のv1.1を確認し、Spotifyを手動で再生してから「テスト再生」で比較してください。すでに停止したSpotifyをページから再開する機能はありません。設定変更は再生・待機が終わってから行えます。ログのAudio Sessionには要求値・設定値・状態を記録します。iPhone実機での改善は未確認です。
