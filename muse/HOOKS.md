# フックによる単発監視

外部の実行基盤から20秒間隔で以下を呼ぶ。フック自体の登録はMuseが行う。

```bash
/path/to/repo/muse/hook_once.sh --config /path/to/coach_config.json
```

スクリプトは1回実行して終了する。内部に20秒のsleepループはない。
起動のたびにプラットフォームから新しい通信認証環境とsurrogate利用権限を受け取ること。
秘密値はスクリプトや引数例に記載しない。

1. `.hook.lock` を非待機で取得。重なった起動は何もせず終了。
2. watcher --onceでWorkerのsessionを取得、新規ならキュー初期化・同期とローカルsession配置。
   モニターはspawnしない。開始準備完了でmonitoringを投稿する。
3. ローカルsessionがliveならmonitor --onceを実行。取得1回、判定と必要な送信後に終了。
4. 終了処理中は保存済み段階を再開。待機期限前ならsleepせず次の呼び出しへ持ち越す。
5. ローカルsessionがclosedになったら次回watcherがclosedを投稿する。

標準出力・標準エラーはフック入口で抑制する。監視の診断はcoach_log.jsonlを参照。
通常の送信再試行は維持するため1回が20秒を超える場合がある。その間のフックはスキップ。
20秒は起動要求間隔で、ネットワーク完了まで含めた厳密な取得周期ではない。

## 保存状態と前提

- `coach_state.json`（新設）: キュー名、送信回数・連番・前回送信時刻、ペース履歴、
  給水／距離イベント、開始通知済み、素材残りと使用済み情報、開始時刻。
  処理途中は取得応答と送信予定ID・文面・成功記録も同じファイルに保存する。
  成功記録前に落ちた送信は同じIDで再送し、publisherの置換を使う。
- `session.json` に任意の `queue_session` を追加。外部のWorker session契約は変更しない。
- `finish_state.json` は既存ファイルを使用し、LiveTrack IDだけでなくキュー名で照合する。
  旧状態はキュー名が一致する場合に引き継ぐ。standbyへ切替済みの旧状態には限定的互換あり。
- `poll_state.json`・queue・使用済みコメントなどは既存のまま。
- `.hook.lock` を新設。各watcher/monitorの既存ロックも取得する。
- 同一VM・同一状態ディレクトリ・同一キューを使う。複数VMの同時書き込みは対象外。
- 素材ファイルを途中で更新するときは、単発モードが保存した素材進行状態を考慮すること。
- 旧常駐からの途中切替ではメモリだけの送信進行は復元できない。切替はラン間に行う。

## 切替とロールバック（Museが実施）

1. ラン終了後、旧ウォッチャー・モニターと15分の常駐再起動ジョブを停止する。
2. muse/一式（共通モジュールを含む）を配置し、上記フックを20秒間隔で登録する。
3. 室内LiveTrackで開始準備・継続配信・終了と履歴保存・closed通知を確認する。
4. ロールバックはフックを無効化し、実行中の単発処理が終了したことを確認してから
   `session_watcher.py --config ...` を `--once` なしで起動する。
   常駐版は従来の動作を残しているが、古い通信認証環境の問題も戻るため暫定復旧用途。

起動から約60分後の通信失敗を出口プロキシの資格情報寿命で説明する説は、
提供された調査に基づく仮説。本変更でプラットフォームの認証更新を実測したわけではない。
本番のフック登録・切替・20分以上の実セッション検証はMuse側で行う。
