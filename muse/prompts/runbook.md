# VCM 運用手順書 (Muse へ渡すプロンプト)

Voice Coach for Muse (VCM) の Muse 側の運用手順。
設計原則は **「決まった動きはプログラム、判断と文章は Muse」**。
走行中の配信ループに LLM は入らない。再現性と信頼性はプログラム側が担い、
Muse は開始の段取り、コメント素材の用意、異常時の復旧を担う。

## 全体像

```
Garmin ウォッチ
  └ LiveTrack 開始メール (Gmail)
       ├ [自動] iOS アプリのキック → GAS (gas/) → Worker の session.json
       │          → session_watcher.py → coach_monitor.py
       └ [手動] Muse がメールを検知 → run_watch.py → coach_monitor.py
coach_monitor.py
  ├ livetrack_poll.py で LiveTrack を 20 秒間隔でポーリング
  ├ 文面を組み立て → publish.py (say)
  │     → Muse TTS で音声化 → Cloudflare Worker + R2 のキューへ
  └ iOS アプリがキューをポーリングして再生 (音楽をダッキング)
```

## 文面の型 (固定)

1 通は次の順序を守る。

1. 距離 (小数がある場合は日本語の読みに変換する。例: 3.6 → さん点ろく)
2. 累積平均ペース
3. 心拍の判定 (数値ではなく「余裕あり / 適正 / 少し高め / 高め」)
4. コメント 1 つ (comment_stock.json から。使用済みは used_comments.json に
   永続化され、同じランでも別の日でも繰り返さない。ペース逸脱など
   重要な注意のみ例外)

コメントは「仲間と一緒に走っている」感覚のものにする。その日の場所・
天気・本人の目標や予定を織り交ぜると単なる数値読み上げと差別化できる。

## 起動モード A: 自動チェーン

前提: GAS がデプロイ済み、Worker に session 取り込み対応版が入っている、
session_watcher.py が常駐している。

- ウォッチャーは Worker の GET /session.json を認証付きでポーリングし、
  受信から 20 分以内の新しいセッションを見たら監視を自動起動する。
- Muse の仕事は「常駐が生きているかの確認」だけ。ラン予定の前に
  ウォッチャーのログ鮮度とプロセスを確認し、死んでいたら再起動する
  (VM 入れ替え等で落ちることがある)。
- ラン開始前にキューをそのラン専用のセッション名で初期化する
  (publish.py init)。前回の名前が残っているとアプリ側で再生エラーや
  既読扱いが起きる。

## 起動モード B: チャットから依頼されたとき

1. その日の練習内容と目標ペース帯を確認する。
2. run_watch.py を起動する。内部で wait_announce.py が待機音声を
   1 分間隔で流し、Gmail の開始メールを検知したら監視へ移る。
3. **開始メールの URL 抽出は必ず HTML 本文から行う**。通常の整形表示では
   リンク URL が落ち、検知が数分遅れた実例がある。短縮リンク (gar.mn) は
   リダイレクト先を解決してから抽出する。
4. 検知したらユーザーに「監視を開始しました」と 1 回だけ伝える。

## 走行中

- 監視プログラムが全て行う。Muse が様子を聞かれたら coach_log.jsonl と
  poll_state.json を読んで答える (推測で答えない)。
- LiveTrack API の一時的な応答途切れは起きる。poll_fail_abort は 30
  (20 秒間隔で約 10 分) に設定し、短い途切れで終了扱いにしない。

## 終了と後片付け

- 終了判定はセッション情報の確定、または track-points が 403
  (理由コード 1008 = アクセス終了) を返した時点で即時に行う。
- 終了文面は直近の正常値から組む。終了応答に現在の数値が含まれない
  ことがあるため、ゼロから文面を作らない。
- 送信は再送付き (同一 ID で最大 3 回、終了文面は 4 回)。ID が同じなら
  キュー側で重複しないので、再送で二重再生にはならない。
- 終了文面の配信後、約 60 秒待ってから履歴へ保存し、キューを standby に
  戻して音声を掃除する。即時に切り替えるとアプリが最終メッセージを
  取得できない。

## 復旧

監視プロセスが途中で死に、セッションが live のまま残ったら
finalize_run.py を実行する。最終ポイントから終了文面を組み、待機 →
standby 切替 → 掃除 → セッションを closed にする。最終ポイントが
新しい (既定 120 秒未満) 場合は監視が生きている疑いとして拒否する。

## セキュリティ

- LiveTrack のトークンは「リンクを知る人が現在位置を見られる」資格情報。
  状態ファイル以外に書き出さない。チャットやリポジトリに載せない。
- queue.json は公開読み取りされる前提の置き場。入れてよいのは
  コーチング文と音声ファイル名だけ。位置情報・トークン・個人情報を
  絶対に入れない。
- Worker へのアップロードトークンはシークレット管理 (Muse では
  Secure Vault / カスタムコネクタ経由) で渡し、コードに書かない。
