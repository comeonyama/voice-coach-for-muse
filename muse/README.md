# VCM — Muse 側 (muse/)

Voice Coach for Muse の「頭脳」側一式。Garmin LiveTrack を監視し、
走行中に音声コーチングを生成して配信キューへ流すプログラム群と、
発話エージェントへ渡すプロンプトを含む。

受信側の iOS アプリはこのリポジトリのルート側にある。アプリがキューを
ポーリングして音声を再生し、再生中は音楽をダッキングする。

導入の依頼と確認は [SETUP.md](../SETUP.md)、ラン中に併走する発話エージェントへの指示は [insert-agent.md](prompts/insert-agent.md) を使う。この文書は、Muse 側のプログラムを配置・運用する際の参照資料。

## 構成

| ファイル | 役割 |
|---|---|
| `livetrack_poll.py` | LiveTrack API のポーリング。セッション情報と軌跡を取得し、距離・時間・心拍・スプリットを JSON で返す |
| `coach_monitor.py` | 監視ループ本体。文面の組み立て、送信タイミング、終了処理、再送を担う |
| `publish.py` | 発行係。Muse TTS で音声化し、Worker（データの受け渡し）のキューへ上げる (ローカルミラーも保持) |
| `session_watcher.py` | `--once`で開始準備と状態反映。常駐モードはロールバック用に保持 |
| `run_watch.py` | 手動開始用。待機音声を流しながら開始メールを検知し、監視へ渡す |
| `wait_announce.py` | 検知までの待機音声 (run_watch から起動される) |
| `finalize_run.py` | 監視が途中で死んだ場合の復旧。最終ポイントから終了処理を完遂する |
| [prompts/insert-agent.md](prompts/insert-agent.md) | 定型コーチングと併走する発話エージェントへ渡すプロンプト |
| `config.sample.json` | 監視設定の雛形 |
| `comment_stock.sample.json` | コメント素材の雛形 (実運用では自分の言葉に差し替える) |

## セットアップの参照先

構築手順と Muse への依頼文は [SETUP.md](../SETUP.md) にまとめている。監視プログラムの配置は [ステップ6](../SETUP.md#step-6)、発話エージェントの併走準備は [ステップ7-2](../SETUP.md#step-7-agent) を参照する。フックの実行方式・状態保存・復旧は [HOOKS.md](HOOKS.md) に記載する。

## コーチングの役割分担

スクリプト層は「距離 → 累積平均ペース → 心拍の判定 → コメント1つ」の順で定型コーチングを作る。小数の距離は日本語の読みに変換する（例：3.6 → さん点ろく）。文面の方針は [README のコーチング指示](../README.md#muse-へのコーチング指示)を参照する。

コメント素材は `comment_stock.json` やラン用の素材ファイルで用意する。通常素材の使用履歴は `used_comments.json` に保存し、同じ状態ディレクトリを使うラン間でも重複を避ける。重要な注意などは別の判定に従う。単発実行の素材進行状態については [HOOKS.md](HOOKS.md) を参照する。

発話エージェントはスクリプトと別に実行し、その場に合わせた発話を挿入する。定型コーチングの固定順は適用しない。条件と指示は [専用プロンプト](prompts/insert-agent.md) にまとめている。

## チャットから手動で開始する場合

標準はアプリ → GAS → Worker → 監視フックの自動経路。手動で開始メールを検知する場合には `run_watch.py` を使う。今回の練習内容・目標ペースと実行環境を確認し、自動経路と同じランの監視を二重に起動しない。

`run_watch.py` は Muse 環境の Gmail CLI を使い、`wait_announce.py` で待機音声を約1分間隔で流して、開始メールの検知後に監視へ渡す。メールのリンクは **HTML 本文から抽出**する。整形済みの本文では URL が欠落することがある。`gar.mn` の短縮リンクはリダイレクト先を解決する。引数は `python3 run_watch.py --help` を参照する。

手動経路にアプリの `start_id` がなければ、アプリの監視中表示は更新されない。開始の成否は実行記録で確認し、ユーザーへの開始報告は1回にする。

## 情報の扱い

- LiveTrack のトークンは現在位置へアクセスできる資格情報。必要な状態ファイルで管理し、チャットやリポジトリへ載せない。
- 公開されるキューの文面・音声には、位置情報・トークン・公開できない個人情報を含めない。発話エージェントが予定などを材料にするときも同様。
- Worker のアップロードトークンは Muse のシークレット管理・カスタムコネクタを使い、コードに書かない。

## このパッケージに含まれないもの

- 実運用の設定ファイル (`coach_config.json`) とコメント素材の実物
- 実行時状態 (セッション情報、ポーリング状態、使用済みコメント、ログ)
- トークン類 (LiveTrack トークン、アップロードトークン)

これらをリポジトリに追加しないこと。ルートの `.gitignore` はすべての保存場所を網羅していないため、状態・設定の配置先と `git status` を確認する。

単発モードは `coach_state.json` に送信ルールの進行状態と実行途中の送信を保存します。
監視サイクルは各回で終了し、認証はフック実行時の環境から受け取ります。

## 高度を使ったコーチング

`config.sample.json` を実運用の `coach_config.json` に反映するときは、次の `altitude` 設定を使います。項目を省略した場合も同じ既定値です。

| 設定 | 既定値 | 用途 |
|---|---|---|
| `altitude.enabled` | `true` | 高度をコメント判定・終了文面に使う。`false` でもポーラーの高度収集は継続 |
| `altitude.downhill_net_loss_m` | `20` | 直近の完了kmで「下降量−上昇量」がこの値以上なら、速すぎ指摘を抑制 |
| `altitude.climb_gain_m` | `20` | 直近kmの上昇量がこの値以上なら、上りコメントの候補にする |
| `altitude.finish_ascent_m` | `50` | 累積上昇量がこの値以上なら、終了文面に獲得標高を添える |

単位はメートルです。下りによる抑制はkm境界から150m以内に限定し、古い下りの情報を次の区間へ引きずらないようにしています。瞬間的な勾配判定ではないため、区間途中の坂の変化を完全には反映しません。上りコメントは、そのkmに対応する間だけ、重要な注意・節目・通常素材の後、汎用コメントの前に選びます。通常素材がある間は上りコメントは出ません。メッセージの背骨と心拍バンドは変えません。

ポーラーは `altitude` を読み、スプリットに `elev_gain_m` / `elev_loss_m`、statusに `current_altitude_m` / `total_ascent_m` を追加します。最新の完了スプリットは `last_elevation_split` としても返し、kmをまたがない取得でも参照できます。

`ALTITUDE_DEADBAND_M = 2.0` は最後に採用した高度との差が2m未満なら累積しない方式です。比較基準を毎ポイント更新しないため、1mずつの緩い上りも累積できます。採用した高度差を現在のポイント間の距離比でkmへ配分するため、境界付近には配分の近似誤差があります。2m以上のノイズや長期ドリフトは除去できず、獲得標高は推定値として「約」を付けて伝えます。

高度が欠けた点や非数値・非有限値は飛ばし、その前後の高度差を推測して加算しません。最終点の高度が欠けると `current_altitude_m` は `null` です。必要な基準値・累積値は `poll_state.json`、監視側の直近スプリット・累積上昇量は `coach_state.json` に保存し、単発実行をまたいで引き継ぎます。旧stateは既定値で読めますが、アップデート以前や欠損区間の高度は復元しないため、そのランの総上昇量が少なくなる場合があります。切替はラン間に行ってください。

合成ポイントによるPythonテストで累積・再開・判定を確認しています。実際のLiveTrack高度の精度、坂でのコメントと終了音声の聴取は、本番配置後にMuse側で検証してください。

## 発話間隔

標準設定のひな形は `send_mode: "interval"` / `send_interval_sec: 180`（3分）です。既存configの指定値は変更せずに使えます。距離モードは `send_mode: "distance"` と `send_distance_km: 0.5` または `1.0`。旧 `per_km` は距離1kmの別名として受け付けます。距離モードは初回300m以降、成功した前回送信地点から指定距離進むたびに1件送り、複数区間を飛び越えても連続送信しません。失敗した送信では地点を進めません。

セッションの `speech_interval` が `per_km` / `per_500m` / `interval:180` ならconfigより優先します。指定なし・不正値はconfigへ戻ります。アプリ→GAS→Worker→watcher→ローカルsessionの順に更新し、monitorは各サイクルで同じランのローカルsessionを読み直します。現在の単発フック経路で反映するためwatcherも更新してください。旧常駐経路でのラン中同期は対象外です。

`coach_state.json` の `last_send_distance_km` は成功した実際の送信地点です。旧stateにない場合は `last_send_km` から移行します（旧stateに保存されなかった小数部分は復元できません）。切替では前回の送信地点・時刻を保持します。ポーラーの `distance_km` は既存の小数距離を利用し、kmスプリットは高度判定用に維持します。500mのためにkmスプリットの意味を変えません。

Workerの設定更新は開始IDを照合し、R2の条件付き書き込みで読み取り後のセッション変更も検出します（[R2公式API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)）。新しいランへの古い設定の書き戻しを防ぎ、競合は次回のGASスクリプト実行時に再試行します。
